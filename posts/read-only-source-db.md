# 원천 DB는 읽기만 — 실수로도 쓰지 못하게 일곱 겹으로 막기

데이터 분석 서비스를 만들면서 회사의 다른 서비스 DB를 읽어야 했습니다. 운영 DB도 포함돼 있었습니다. 분석 서비스는 자기 DB를 따로 갖고, 원천에서는 필요한 집계만 가져오는 구조였습니다.

처음 정한 원칙은 간단했습니다. **원천 DB는 조회만 한다. 어떤 변경도 하지 않는다.**

어려운 것은 이 원칙을 매일 지키는 일이었습니다. 여러 개발자와 AI 코딩 에이전트가 코드를 수정하고, 테스트를 돌리고, 확인용 명령을 실행합니다. 그때마다 연결 대상을 정확히 보고 올바른 명령만 실행하리라고 기대하기는 어려웠습니다.

그래서 실수할 수 있다는 전제에서 시작했습니다. 잘못된 계정을 넣거나, 테스트 설정을 놓치거나, 에이전트가 확인용 쿼리를 실행하더라도 다음 장치가 막도록 방어를 겹쳤습니다.

## 쓰기 금지의 범위부터 정했다

처음에는 INSERT, UPDATE, DELETE만 막으면 될 것처럼 보입니다. 하지만 원천을 건드릴 수 있는 경로는 그보다 많았습니다.

테이블과 뷰, 인덱스, 함수를 만드는 일도 금지했습니다. 임시 테이블도 예외로 두지 않았습니다. 권한이나 서버 설정을 바꾸는 명령, 프로세스를 종료하는 명령도 허용하지 않았습니다. `SELECT … FOR UPDATE`처럼 조회 모양을 하고 있어도 명시적으로 잠금을 거는 쿼리는 제외했습니다.

애플리케이션 밖의 경로도 봤습니다. 원천 연결을 대상으로 마이그레이션이나 시더를 실행하면 안 됩니다. 데이터를 바꾸지 않더라도 합의 없이 운영 리더에 무거운 집계를 날리는 일은 막아야 했습니다. 읽기 전용이라는 말이 운영 부하까지 없애주지는 않기 때문입니다.

여기에 한 가지를 더 명시했습니다.

> 쓰기가 막히는지 확인하려고 쓰기를 시도하는 것도 금지한다.

임시 테이블 하나를 만들어 보고 거부되는지 확인하는 방법은 직관적입니다. 하지만 권한이 잘못돼 있다면 그 확인이 성공하는 순간 원천에 변경이 생깁니다. 안전장치가 제대로 설정됐는지 알아보려다, 안전장치가 없는 경로를 직접 실행하게 됩니다.

그래서 차단 여부는 권한과 설정 값을 조회해서 확인하도록 했습니다. 실제 원천에 변경 명령을 보내는 방식은 검증 절차에서 뺐습니다.

## 방어는 연결부터 작업 절차까지 이어진다

전체 구조는 다음과 같습니다. 앞의 장치가 잘못 설정되거나 우회되더라도 뒤에서 다시 제한하도록 구성했습니다. 다만 일곱 겹이 모두 같은 일을 하는 것은 아닙니다. 계정과 세션은 실행 권한을 제한하고, 테스트 격리는 접속 자체를 막고, 코드 검사는 잘못된 경로가 들어오는 것을 잡습니다.

## 1. 계정: 조회 권한만 준다

원천마다 분석 서비스 전용 계정을 따로 두고 SELECT 권한만 부여했습니다. 기존에 사용하던 넓은 권한의 계정은 서비스 설정에서 제거했습니다.

이것이 가장 기본적인 방어입니다. 애플리케이션에서 잘못된 SQL을 만들어도 DB가 권한으로 거부해야 합니다. 개발자가 주의하는 것보다 실제 권한을 줄이는 편이 확실합니다.

다만 계정 하나에 모든 것을 걸지는 않았습니다. 설정에 다른 계정이 들어갈 수 있고, 나중에 권한이 바뀔 수도 있습니다. 그래서 연결 대상도 제한했습니다.

## 2. 엔드포인트: 쓰기 주소를 설정에 넣지 않는다

원천 연결은 리더·레플리카로 한정하고, 쓰기 엔드포인트는 설정 파일에 아예 넣지 않았습니다. 선택할 필요가 없는 주소를 남겨두면 잘못 선택할 경로도 남습니다.

여기서 중요한 것은 주소 이름에 ‘reader’가 붙어 있다는 사실보다, 실제 대상이 쓰기를 제한하는 읽기 전용 복제본인지입니다. DB와 관리형 서비스의 구성에 따라 보장 범위가 다르므로, 연결 대상의 설정도 조회해 확인해야 합니다.

계정 권한과 연결 대상은 별도로 봤습니다. 조회 계정을 쓰는 것과 읽기 전용 대상에 붙는 것을 함께 만족하도록 했습니다.

## 3. 세션: 연결할 때 한 번 더 제한한다

연결을 맺을 때 세션을 읽기 전용 트랜잭션 모드로 설정하고, 쿼리 제한 시간도 걸었습니다. 앞의 두 조건이 잘못됐더라도 실행 세션에서 다시 제한을 적용하려는 목적이었습니다.

읽기 전용 모드가 정확히 무엇을 막는지는 DB마다 다릅니다. 임시 객체나 일부 명령이 예외일 수도 있어서, 이 설정 하나로 우리가 정한 모든 금지 행위가 차단된다고 보지는 않았습니다.

제한 시간 역시 쓰기 방지와는 역할이 다릅니다. 조회만 하는 쿼리도 오래 실행되면 원천에 부담을 줍니다. 권한을 제한하는 것과 조회 부하를 제한하는 것을 함께 다뤘습니다.

## 4. 테스트 격리: 테스트는 원천에 닿지 못하게 한다

테스트에서는 원천 접속 정보를 존재하지 않는 호스트와 빈 계정으로 강제로 덮어썼습니다. 분석 서비스 자체의 DB는 메모리 DB를 사용했습니다.

“테스트할 때 운영 환경 변수를 쓰지 않는다”는 약속만으로는 부족했습니다. 로컬 셸에 남아 있는 환경 변수가 무엇인지, 테스트 프레임워크가 어떤 설정을 먼저 읽는지 매번 기억하고 싶지는 않았습니다. 테스트 설정이 외부 값을 덮어쓰도록 했습니다.

그리고 격리 설정이 실제로 적용됐는지 확인하는 테스트를 별도로 뒀습니다. 이 검사가 실패하면 나머지 테스트를 실행하지 않도록 순서도 정했습니다. 안전하게 격리돼 있다는 전제가 틀렸다면, 그 상태로 다른 테스트를 계속 돌릴 이유가 없었습니다.

이 검사는 원천에 접속해서 실패하는지 보는 방식이 아닙니다. 테스트 프로세스에 적용된 접속 설정이 격리 값인지 확인합니다.

## 5. 코드 경계: 원천 연결을 쓸 수 있는 곳을 좁힌다

원천 연결 이름은 데이터를 가져오는 모듈 안에서만 사용할 수 있게 했습니다. 마이그레이션, 시더, 모델, 팩토리에서 원천 연결을 참조하면 아키텍처 테스트가 실패하도록 했습니다.

원천용 SQL도 별도 파일로 모았습니다. SELECT나 WITH로 시작하는지, 금지한 구문이 들어 있지 않은지 검사하고 `SELECT *`도 금지했습니다. 어떤 컬럼을 읽는지 파일에 명시하도록 한 것입니다.

물론 SELECT나 WITH로 시작한다는 사실만으로 안전한 조회가 되는 것은 아닙니다. DB에 따라 WITH 안에 변경 구문이 들어가거나 조회에서 호출한 함수가 부수 효과를 낼 수도 있습니다. 문자열과 키워드 검사는 잘못된 코드가 들어오는 것을 줄이는 보조 장치로 두고, 실제 제한은 DB 권한과 실행 설정에 함께 맡겼습니다.

이 경계는 리뷰어가 매번 기억해서 검사하게 하지 않았습니다. 아키텍처 테스트가 매 빌드에서 확인하게 했습니다. 잘못된 연결 참조가 한 줄 추가돼도 자동으로 드러나야 했습니다.

부수 효과도 있었습니다. SQL 파일만 보면 원천에서 어떤 데이터를 어떤 모양으로 가져오는지 알 수 있었습니다. 컬럼을 명시하니 스키마 변경의 영향을 추적하기도 쉬워졌습니다. 원천 스키마가 바뀌었을 때 실제로 드러나는 시점은 쿼리를 검증하거나 실행할 때지만, 적어도 변경의 영향을 살펴볼 위치는 분명해졌습니다.

## 6. 실행: 조회를 검증하고, 끝나면 롤백한다

가져오기 실행기는 실행 직전에 SQL이 단일 조회 문장인지 다시 확인합니다. 코드가 저장소에 들어올 때 검사하는 것에 더해, 실제 실행 경로에서도 확인하는 것입니다.

원천 쿼리는 읽기 전용 트랜잭션 안에서 실행하고, 성공하든 실패하든 종료 시 롤백하도록 했습니다. 원천에서 읽는 경로에는 커밋할 일이 없다는 구조를 코드로 표현했습니다.

여기서 롤백을 최후의 복구 수단으로 생각하면 안 됩니다. DB에 따라 트랜잭션으로 되돌릴 수 없는 명령이나 외부 부수 효과가 있습니다. 그래서 먼저 변경을 실행한 뒤 롤백하면 된다는 접근은 허용하지 않았습니다. 권한과 조회 검증으로 실행 전에 막고, 롤백은 그 위에 더한 종료 절차였습니다.

## 7. 사람과 에이전트: 직접 조회하는 방법도 정한다

애플리케이션 경로를 막아도 사람이 직접 DB 클라이언트를 열 수 있습니다. AI 코딩 에이전트가 터미널에서 쿼리를 실행할 수도 있습니다. 그래서 직접 확인할 때의 절차도 같은 원칙으로 정했습니다.

읽기 전용 트랜잭션을 사용하고, 허용한 조회 문장과 제한 시간을 지킵니다. 큰 테이블은 바로 집계부터 하지 않고 크기를 먼저 봅니다. 무거운 집계가 필요하면 실행 시간대를 합의합니다. 단순한 조회 권한이 모든 조회를 마음대로 실행해도 된다는 허가는 아니었습니다.

사고가 의심될 때의 행동도 정해뒀습니다.

> 원천에 변경이 생겼을 가능성이 있으면 즉시 멈추고 보고한다. 되돌리려고 추가 명령을 실행하지 않는다.

잘못 실행했다는 생각이 들면 곧바로 고치고 싶어집니다. 하지만 어떤 변경이 실제로 반영됐는지 모르는 상태에서 추가 명령을 보내면 상황을 더 복잡하게 만들 수 있습니다. 복구 판단은 실행을 멈추고 상태를 확인한 뒤에 해야 했습니다.

## 에이전트가 기억하지 못해도 남아 있어야 하는 장치

이 프로젝트는 AI 코딩 에이전트와 함께 개발했습니다. 에이전트는 문제를 만나면 직접 실행해서 확인하려는 흐름으로 이어지기 쉽습니다. 원천 DB에서는 그 확인 방법 자체를 제한해야 했습니다.

프로젝트 규칙 문서 맨 앞에 이 내용을 절대 규칙으로 적고, 매 세션 읽게 했습니다. 특히 차단 확인용 쓰기 시도 금지와 사고 의심 시 중단 규칙은 명시적으로 남겼습니다.

하지만 문서를 읽히는 것으로 끝내지는 않았습니다. 규칙을 놓쳐도 조회 계정이 남아 있고, 테스트는 원천 설정을 덮어쓰고, 잘못된 연결 참조는 빌드에서 잡히도록 했습니다. 어느 한 겹도 모든 경우를 보장하지는 않습니다. 서로 다른 실패 경로를 막는 장치를 함께 유지하는 것이 목적이었습니다.

이 구조를 만들면서 가장 많이 되물은 질문은 “다들 조심할 수 있나?”보다 “누군가 실수하면 어디에서 멈추나?”였습니다. 원천 DB에 대해서는 그 답이 사람의 기억이나 대화 한 줄에만 남아 있지 않게 하고 싶었습니다.
